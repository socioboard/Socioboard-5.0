## Staging (PM2)
Decided 2026-10-06: staging is one server (8 vCPU, 8 GB RAM) running the apps under PM2 from a checkout of the repo, not the Docker images, with the services installed on it. Production and self-host keep the images. Files: `deploy/staging/`.

| What | Where | Port |
| --- | --- | --- |
| `socioboard-web` | PM2's static server for `apps/web/dist`, app routes → `index.html` | 3001 |
| `socioboard-api` | `node apps/api/dist/main.mjs` | 3000 |
| `socioboard-worker` | `node apps/worker/dist/main.mjs` (takes no traffic) | none |
| PostgreSQL 17, Valkey 8.1, OpenObserve v1.0.4, Node 24, ffmpeg 5.1+ | Installed on the server; Valkey with `appendonly yes` and `maxmemory-policy noeviction` (scheduled posts are its jobs) | internal only |

- **One host:** `app-dev.socioboard.ai`. nginx (`deploy/staging/nginx.conf`) sends `/api/` (WebSockets included) and `/public-media/` to 3000 and everything else to 3001, so the session cookie stays first-party and the networks' callbacks and media links are on the app's host. `MEDIA_PUBLIC_URL=https://app-dev.socioboard.ai/public-media`; TikTok verifies that URL prefix. `TRUST_PROXY=loopback` (nginx is on the same machine).
- **Processes** (`deploy/staging/ecosystem.config.cjs`): one fork-mode instance each (live updates hold sockets per process), settings from `SOCIOBOARD_ENV_FILE` (default `/etc/socioboard/staging.env`, outside the checkout) through Node's `--env-file`. PM2 stops them with SIGINT and waits 40 s; the apps finish in-flight requests and jobs and exit within 35 s.
- **Deploy** (`deploy/staging/deploy.sh`, as the deploy user): fast-forward the checkout, `pnpm install --frozen-lockfile`, `pnpm build`, `pnpm db:deploy`, `pm2 startOrReload … --update-env`, `pm2 save`, then wait for `/api/health`. It stops rather than lose local changes on the server.
- **Checked 2026-10-06** on a workspace checkout: all three processes start and reload under PM2, `/api/health` 200, app routes served by the web process, the nginx file passes `nginx -t`. The first run found the built API couldn't find Bull Board's UI files outside the image's flat `node_modules`; `bullBoardUiPath` now falls back to resolving through `@socioboard/core`.

## Public media address
`media.<domain>` (and the dev tunnels) must proxy to the API's `/public-media` path, e.g. Caddy `media.socioboard.com { rewrite * /public-media{uri}; reverse_proxy api:3000 }`, with `MEDIA_PUBLIC_URL=https://media.socioboard.com`. Networks that fetch media themselves (Instagram images, TikTok) read files there; addresses are signed and expire (see [media](backend/modules/media.md#delivering-media-to-networks-p1-b8)). TikTok's URL-prefix verification covers `https://media.socioboard.com/`.

## Observability
Decided 2026-10-05: no paid services, so no hosted Sentry or Grafana Cloud. The code speaks open standards (OpenTelemetry), so the backend is a deployment choice.

- **Switch:** `OTEL_EXPORTER_OTLP_ENDPOINT` (e.g. `http://127.0.0.1:5080/api/default` for OpenObserve; the base its `/v1/traces`, `/v1/metrics` and `/v1/logs` hang off). Unset, nothing is exported and the SDK isn't started. `OTEL_EXPORTER_OTLP_HEADERS` adds headers (a backend's ingestion key) and `OTEL_RESOURCE_ATTRIBUTES` adds attributes, as in every OpenTelemetry SDK.
- **What is sent:** services `socioboard-api` and `socioboard-worker` with `deployment.environment.name`. Traces: one span per API request named by its route (`POST /api/v1/workspaces/:workspaceId/posts`), database queries (Prisma), outgoing calls to the networks (`fetch`, query strings removed since they can carry tokens), queue jobs linked to the request that queued them (BullMQ). Logs: every Pino line (already redacted) with its trace. Metrics: `http.server.request.duration`, `socioboard.publish.deliveries` (by network and outcome), `socioboard.queue.jobs` (by queue and state, from the worker). Exceptions: unhandled API errors (500), failed jobs, crashes, and browser errors.
- **Why not auto-instrumentation:** the api and worker images are bundles (tsdown), so libraries can't be patched as they load; every source above works on bundled code.
- **Backend: OpenObserve** (decided 2026-10-05, lowest cost and resources; AGPL-3.0, free to self-host; we don't modify or redistribute it). One container with its data on disk (or S3): traces, logs, metrics, dashboards and alerts. Measured here with the whole browser suite: about 180 MB of RAM idle and 390 MB under the load, against about 1.75 GB for SigNoz (ClickHouse and ZooKeeper). Errors show as exceptions on spans and as error logs, without Sentry-style issue grouping.
- **OpenObserve locally:** `docker run -d --name openobserve -p 5080:5080 -v openobserve-data:/data -e ZO_DATA_DIR=/data -e ZO_ROOT_USER_EMAIL=<you> -e ZO_ROOT_USER_PASSWORD=<password> public.ecr.aws/zinclabs/openobserve:latest` (the open-source image; `openobserve-enterprise` is another licence), UI at http://localhost:5080. Then `OTEL_EXPORTER_OTLP_ENDPOINT=http://127.0.0.1:5080/api/default` (`default` is the organisation) and `OTEL_EXPORTER_OTLP_HEADERS=Authorization=Basic%20<base64 of email:password>` (the space written `%20`). Use `127.0.0.1`: `localhost` resolved to IPv6 on Windows and wasn't forwarded.
- **OpenObserve is strict:** it refuses a whole batch (400 "Invalid data for Value") when one attribute has no value, where SigNoz shrugs. BullMQ adds `bullmq.job.result: undefined` to every job that returns nothing, which lost all worker job spans until `platform/queue` dropped empty event values (`withoutEmptyEventValues`, with a test). `OTEL_LOG_LEVEL=warn` prints such refusals on stderr; unset, the SDK is silent.
- **SigNoz instead** (heavier, nicer error views): the community edition is MIT. It installs with Foundry now (`signoz.io/docs/install/docker`, WSL 2 on Windows); v0.129.0 is the last release with a plain compose in `deploy/docker`. Create its first account at http://localhost:8080 before sending anything (until then the collector drops connections), then `OTEL_EXPORTER_OTLP_ENDPOINT=http://127.0.0.1:4318`.
- **Checked on 2026-10-05** with the whole browser suite against both (OpenObserve v1.0.4, SigNoz v0.128): request and job spans with one trace from an api request through the worker's job, Prisma and Better Auth's own spans, logs with their trace ids (90 of 101), the metrics above with BullMQ's job metrics, and a browser error as an exception; no tokens or OAuth codes in any span or log. The built api and worker bundles were run the same way.
- **Alerts** (built in, `modules/admin`): see [admin](backend/modules/admin.md#alerts-p2-i1).
